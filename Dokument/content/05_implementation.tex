\chapter{Implementierung}
\label{ch:Implementierung}

Dieses Kapitel beschreibt die technische Umsetzung der Komponenten Runtime Node und Runtime Master sowie die simulative Evaluierung der Scheduling-Methoden.

\section{Implementierung Runtime Node}
\label{sec:ImplementierungRuntimeNode}

Die Komponente Runtime Node wird auf Fahrzeugsteuergeräten ausgeführt, weshalb deren spezifische Anforderungen bei der Implementierung berücksichtigt werden müssen. Die Wahl der Programmiersprache erfolgte unter den Gesichtspunkten einer möglichst hohen Kompatibilität mit benötigten Softwarebibliotheken sowie der Kompilierbarkeit auf diversen Hardwarearchitekturen. 

In \autoref{ch:MethodeSoftwareplattform} wurde festgelegt, dass der Runtime Node ein Linux-Kernel-basiertes Betriebssystem voraussetzt. Da der Kernel dieser Systeme in der Programmiersprache C implementiert ist, bietet diese Sprache im Vergleich zu anderen weit verbreiteten Sprachen wie C++, Java, Python oder Rust eine deutlich höhere Hardwarenähe. Gängige C-Compiler wie GCC, Clang/LLVM oder MSVC unterstützen nahezu alle relevanten Hardwarearchitekturen. Auch für spezialisierte Plattformen im Embedded-Bereich existiert sehr häufig eine proprietäre C-Toolchain. Aus diesem Grund eignet sich die Programmiersprache C hervorragend für die Implementierung des Runtime Node. 

Die Softwareentwicklung erfolgte in einer Linux-Entwicklungsumgebung auf einem Desktop-PC. Diese Umgebung ist ausreichend, da Linux als Betriebssystem für die Fahrzeugsteuergeräte vorausgesetzt wird und somit die Kompatibilität der Software gewährleistet ist. Im Folgenden werden die konkreten Vorgehensweisen zur Implementierung der einzelnen Softwaremodule des Runtime Node beschrieben.

\subsection{Implementierung des Container Management}
\label{sec:ContainerManagement}

Das Container Management ist für die Erstellung und Verwaltung isolierter Laufzeitumgebungen für externe Anwendungen zuständig. Dabei kommt die Containerisierung als Isolierungsmethode zum Einsatz. Bei dieser Methode werden native Linux-Kernel-Funktionen genutzt, um eine isolierte Laufzeitumgebung zu erstellen, die als Container bezeichnet wird. Das Container Management implementiert vier Hauptfunktionen:

\begin{itemize}
    \item Container erstellen
    \item Container starten
    \item Container stoppen
    \item Container löschen
\end{itemize}

Die Erstellung eines Containers wird durch einen entsprechenden Befehl ausgelöst. In diesem Befehl muss ein Containername definiert werden, der anschließend intern zur Identifikation des Containers verwendet wird. Zunächst wird validiert, ob ein Container mit demselben Namen bereits angelegt wurde. Ist dies der Fall, wird kein neuer Container erstellt und eine entsprechende Fehlermeldung an den Runtime Master kommuniziert. Existiert kein Container mit dem gleichen Namen, wird ein neuer Ordner angelegt. Dieser dient als Wurzelverzeichnis (\textit{Root Directory}) für die Applikation im Container. Der Runtime Node kann eine Standardvorlage für ein solches Wurzelverzeichnis bereitstellen und dessen Inhalt in jeden neuen Containerordner kopieren. Dies kann beispielsweise das Dateisystem einer minimalen Linux-Distribution beinhalten, damit die Applikationen die Standardbibliotheken und Werkzeuge eines Betriebssystems direkt nutzen können. Nach der Erstellung des Containers kann der Runtime Master sowohl Applikationen als auch weitere Softwarebibliotheken über das Kommunikationsinterface in den Containerordner übertragen.

Die technische Isolierung der Applikationen erfolgt über Linux-Kernel-spezifische Funktionen. Für Unix-basierte Betriebssysteme wie Linux wurde der \gls{POSIX}-Standard entwickelt, um die Kompatibilität von Software zu erhöhen, die auf Betriebssystemfunktionen zugreift. Er definiert eine einheitliche \gls{API} für Kommandozeilen- und Shell-Funktionalität. Die \gls{API} besteht aus C-Funktionen, die in der implementierten Software über die entsprechenden Header-Dateien verwendet werden können. Um die Kompatibilitätsanforderungen zu erfüllen, verwendet die Runtime Node-Komponente, sofern möglich, die standardisierten \gls{POSIX}-\gls{API}-Funktionen zur Isolierung von Anwendungen.

Ein Container wird gestartet, indem eine der darin vorhandenen Applikationen ausgeführt wird. Ein Container kann prinzipiell mehrere Applikationen beinhalten, allerdings sieht die aktuelle Implementierung vor, dass der Runtime Master nur eine Applikation pro Container starten kann. Ein Startbefehl definiert den Namen des Containers sowie den Namen der zu startenden Applikation. Zunächst wird im Runtime Node überprüft, ob ein Container mit dem im Startbefehl angegebenen Namen existiert. Wenn diese Voraussetzung erfüllt ist, wird geprüft, ob eine Applikationsdatei mit dem angegebenen Namen im Container vorhanden ist. Sind beide Voraussetzungen erfüllt, werden die Isolierung und das Starten der Applikationsfunktion vorbereitet. 

Mit der \gls{POSIX}-Funktion \texttt{clone} wird eine als Parameter vorgegebene Funktion als neuer Prozess erstellt, der in den nächsten Schritten vom Betriebssystem isoliert wird. Diese \texttt{clone}-Funktion unterstützt die Isolierung mittels Namespaces, indem die entsprechenden \textit{Unshare Flags}, die in \autoref{ch:StandDerTechnik} näher beschrieben wurden, als Parameter übergeben werden. Die als Funktionsparameter übergebene Funktion wird also durch \texttt{clone} als neuer Prozess mit den vorgegebenen Isolierungsmaßnahmen ausgeführt. Folgende Unshare Flags werden verwendet:

\begin{description}
    \item[\texttt{CLONE\_NEWNS}:] Mount Namespace Unshare Flag (Isolierung der Einhängepunkte).
    \item[\texttt{CLONE\_NEWPID}:] PID Namespace Unshare Flag (Isolierung der Prozess-IDs).
    \item[\texttt{CLONE\_NEWUTS}:] UTS Namespace Unshare Flag (Isolierung von Hostname/Domain).
    \item[\texttt{CLONE\_NEWNET}:] Network Namespace Unshare Flag (Isolierung der Netzwerkressourcen).
\end{description}

Der durch die Funktion \texttt{clone} gestartete Prozess führt anschließend die Routine \textit{Pivot Root} aus, um die Zugriffsrechte des Prozesses auf den Ordnerinhalt des Containers einzuschränken. Hierzu muss der Ordner des Containers ein Mount-Punkt des Prozesses werden. Die Systemfunktion \texttt{mount} fügt den als Parameter übergebenen Pfad als Mount-Punkt dem aktuellen Prozess hinzu. Da für \textit{Pivot Root} keine \gls{POSIX}-standardisierte Wrapper-Funktion existiert, muss sie über die \texttt{syscall}-Funktion implementiert werden. Diese wird über die C-Softwarebibliothek \texttt{glibc} bereitgestellt, die in den meisten Linux-Distributionen enthalten ist. 

Abschließend wird der Prozess mit der \gls{POSIX}-Funktion \texttt{execve} durch die extern geladene Applikation ersetzt. Diese Applikationen werden nun mit allen zuvor angewendeten Isolierungsmaßnahmen im Container ausgeführt. Parallel dazu erzeugt der Runtime Node eine neue \textit{Control Group} (\texttt{cgroup}) für den Prozess. Dies ermöglicht es, Systemressourcen nach Bedarf einzuschränken und alle weiteren Prozesse, die von diesem Host-Prozess erzeugt werden, eindeutig zuzuordnen. Das erfolgreiche Starten der Applikation wird an den Runtime Master zurückgemeldet.

Ein Container kann durch einen externen Befehl gestoppt werden. Existiert der Container mit dem angegebenen Namen und wird aktuell eine Applikation ausgeführt, werden alle Prozesse im Container beendet. Hierzu genügt es, den ursprünglichen Host-Prozess zu beenden, da dieser durch die Isolierung die PID 1 innerhalb des Namespaces erhalten hat. PID 1 wird unter Unix-Systemen als Initialisierungsprozess behandelt. Wird dieser Prozess beendet, werden vom Kernel automatisch alle Kindprozesse ebenfalls beendet.

Das Löschen von Containern erfolgt durch den Befehl \enquote{Container löschen}. Im Befehl muss der Name des Containers angegeben werden. Existiert ein Container mit dem angegebenen Namen im Runtime Node und führt dieser aktuell eine Anwendung aus, so wird er zunächst gestoppt. Anschließend wird der Containerordner inklusive aller extern geladenen Dateien vom Dateisystem gelöscht.

\subsection{Implementierung Befehlsverarbeitung}
\label{sec:ImplementierungBefehlsverarbeitung}

Die Befehlsverarbeitung empfängt \gls{JSON}-Nachrichten von der Kommunikationsschnittstelle, wertet diese aus und führt die entsprechenden Funktionen im Container Management Modul aus. Die \gls{JSON}-Nachrichten werden über den lokalen Kommunikationssockel zwischen dem Node und der Kommunikationsschnittstelle ausgetauscht. 

Zum Parsen und Erstellen von \gls{JSON} wird die Softwarebibliothek \texttt{cJSON} verwendet. \texttt{cJSON} bietet Hilfsfunktionen für die Erzeugung und das Auslesen von \gls{JSON}-Daten. Der Benutzer kann mit Hilfe dieser Funktionen \gls{JSON}-Strukturen selber erstellen sowie Parsing-Funktionen für definierte Strukturen implementieren. Mit Hilfe von \texttt{cJSON} werden Inhalte der Nachrichten in eine interne C-Struktur kopiert und ausgewertet. Die Befehlsnachrichten sind nach dem in \autoref{fig:JSON_command} gezeigten Format definiert. Der Inhalt des Feldes \texttt{Action} bestimmt dabei die auszuführende Operation.

Im nächsten Schritt wird das Feld \texttt{Action} mit den verfügbaren, implementierten Aktionen verglichen. Bei Übereinstimmung wird die entsprechende Funktion im \enquote{Container Management} mit den Parametern aus dem empfangenen Befehl aufgerufen. Unbekannte Befehle werden ignoriert.

Zusätzlich überträgt die Befehlsverarbeitung periodisch eine Statusmeldung namens \texttt{Node\_Info}. Diese Meldung wird von jedem Runtime Node an den Runtime Master gesendet und enthält Informationen über die verfügbaren Rechenkapazitäten sowie über die aktuell laufenden Applikationen. \subsection{Implementierung des Ladens externer Applikationen}
\label{sec:LadenExterneApplikationenNode}

Damit extern bereitgestellte Applikationen auf den Steuergeräten des Runtime Node ausgeführt werden können, müssen die entsprechenden Binärdateien auf das jeweilige Steuergerät geladen werden. Für die prototypische Implementierung wurde dasselbe Kommunikationskonzept für die Übertragung von Dateien verwendet wie für die Übertragung von Befehlen und Statusmeldungen. Die Dateien werden in vorkompilierter Form im Binärformat übertragen. Die Kommunikationsschnittstelle nutzt hierfür \gls{JSON}-Nachrichten. Für die Übertragung wird die in \autoref{fig:JSON_binary} dargestellte Struktur verwendet.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.6\textwidth]{./content/graphics/binaryJSON.pdf}
    \caption{JSON Struktur der Binärübertragungsnachricht}
    \label{fig:JSON_binary}
\end{figure}

Da \gls{JSON}-Nachrichten charakterbasiert sind (in der Regel UTF-8), ist die direkte Übertragung von Binärdaten im Rohformat nicht möglich. Binärwerte müssten als Zeichen dargestellt werden (z.\,B. eine binäre 1 als Zeichen '1'), was extrem ineffizient wäre, da ein Bit Information acht Bits Speicherplatz benötigen würde. Für Anwendungen, in denen Binärdaten in textbasierten Formaten übertragen werden müssen, wurden Binär-zu-Text-Konvertierungsschemen entwickelt. In der Implementierung wurde das Base64-Schema verwendet, das auch im World Wide Web (z.\,B. für E-Mail-Anhänge) weit verbreitet ist. Base64 nimmt sechs Binärwerte und repräsentiert sie mit einem von 64 \gls{ASCII}-Zeichen. Um die Kompatibilität zu erhöhen, nutzt Base64 nur ein Basisset von Zeichen, die von den meisten Anwendungen unterstützt werden. Dadurch wird eine möglichst hohe Portierbarkeit erreicht. Insgesamt werden mit dieser Methode sechs Binärzeichen mit einem 8-Bit-Zeichen kodiert. Die übertragene Datenmenge ist somit um ca. 33\,\% höher als bei der Übertragung von binären Rohdaten.

Die Übertragungslogik ist als Zustandsautomat (\textit{State Machine}) implementiert. Eine Dateiübertragung kann gestartet werden, wenn das Feld \texttt{Action} den Inhalt \texttt{start\_exchange} enthält. Wenn im Feld \texttt{Binary\_Name} kein Name einer bereits existierenden Datei angegeben ist, wird eine neue Datei mit dem definierten Namen angelegt. Eine Bestätigung über das erfolgreiche Anlegen der Datei bzw. eine Fehlermeldung wird an den Runtime Master zurückgesendet.

Nach einer erfolgreichen Bestätigung beginnt der Runtime Master damit, die Binärdaten der Datei zu übertragen. Die Binärdaten werden Base64-kodiert im Feld \texttt{Binary\_Data} übertragen. Dieses Feld hat eine Größe von 3.076 Bytes. Durch die Base64-Kodierung sind davon allerdings nur 2.307 Bytes Nutzdaten. In der Praxis muss eine Datei daher in der Regel auf mehrere Pakete aufgeteilt werden. Während der Übertragung werden die empfangenen Daten dekodiert und in die erstellte Datei geschrieben. Wurden alle empfangenen Bytes erfolgreich geschrieben, wird eine Statusmeldung an den Runtime Master gesendet. Wurde die Datei vollständig übertragen, wird im \texttt{Action}-Feld der Inhalt \texttt{end\_exchange} gesendet. Dies signalisiert dem Runtime Node, dass die aktuelle Datei vollständig übertragen wurde und geschlossen werden kann.

\subsection{Performance-Evaluation des Runtime Node}
\label{sec:PerformanceEvaluationDesRuntimeNode}

Zur Überprüfung der in \autoref{sec:MetrikenundErfolgskriterien} definierten Effizienzmetriken (\enquote{Plattform-Overhead} und \enquote{Reaktionszeit}) wurde der Runtime Node einer experimentellen Untersuchung unterzogen.

Um eine realitätsnahe Bewertung zu ermöglichen, wurden die Messungen auf einer Hardware durchgeführt, die in ihrer Architektur vergleichbar mit modernen Hochleistungssteuergeräten im Automobilbereich ist. Als Referenzplattform diente ein Raspberry Pi 5 mit folgender Spezifikation:

\begin{itemize}
    \item Prozessor: Broadcom BCM2712 (Quad-Core ARM Cortex-A76 @ 2,4 GHz)
    
    \item Arbeitsspeicher: 8 GB LPDDR4X SDRAM
    
    \item Betriebssystem: Raspberry Pi OS (Linux-basiert, Kernel 6.x)
\end{itemize}

Die Wahl einer ARM-basierten Plattform gewährleistet die Übertragbarkeit der Ergebnisse auf automotive SoCs, die überwiegend ebenfalls die ARM-Instruktionssatzarchitektur nutzen.

Um die Reaktionszeit zu bestimmen, wird die Latenzzeit gemessen. Die Latenzzeit (tstartup​) beschreibt die Verzögerung zwischen dem Eingang des start\_container-Befehls und der tatsächlichen Prozessausführung (execve). Die Zeitmessung erfolgte instrumentiert innerhalb des Codes mittels clock\_gettime (CLOCK\_MONOTONIC). Über eine Testreihe von $n=100$ Iterationen wurde eine durchschnittliche Latenz von 1,5 ms bis 1,7 ms ermittelt. Dieser Wert bestätigt, dass die Softwarearchitektur in C keine signifikanten Verzögerungen einführt und Befehle nahezu in Echtzeit verarbeitet werden.

Der Ressourcenbedarf (\enquote{Footprint}) des Runtime Node Prozesses wurde mittels des Analysetools htop unter Standardbedingungen ermittelt:

\begin{itemize}
    \item CPU-Auslastung: Im Leerlauf (Idle) sowie bei reiner Aufrechterhaltung der DDS-Kommunikation war die CPU-Last des Prozesses nicht messbar (Anzeige < 0,1\,\%). Dies belegt, dass die Verwaltungssoftware keine Rechenleistung bindet, die für Fahrfunktionen benötigt wird.
    
    \item Speicherbedarf (RAM): Die Speicherauslastung lag konstant bei ca. 1,5\,\% des verfügbaren Gesamtspeichers (bezogen auf 8 GB RAM). Dieser geringe Speicherabdruck stellt sicher, dass genügend Kapazität für speicherintensive externe Applikationen (z. B. Bildverarbeitung) oder das Training von KI-Modellen verbleibt.
\end{itemize}

 Die Ergebnisse auf der Referenzhardware zeigen, dass der Runtime Node die Anforderungen an eine leichtgewichtige Middleware erfüllt. Mit einem minimalen Overhead bei CPU und RAM sowie Latenzen im einstelligen Millisekundenbereich eignet sich die Implementierung für den Einsatz auf ressourcenbeschränkten Fahrzeugsteuergeräten.

\section{Implementierung der Kommunikationsschnittstelle}
\label{sec:ImplementierungKommunikation}

Die Kommunikationsschnittstelle ist ein eigenständiges Softwaremodul, das ein Publish/Subscribe-Protokoll über das Netzwerk verwendet und eine socketbasierte Schnittstelle mit \gls{JSON} zu den internen Softwarekomponenten nutzt. In \autoref{ch:MethodeSoftwareplattform} wurde das Kommunikationsprotokoll Publish/Subscribe und die konkrete Implementierung \gls{DDS} (\textit{Data Distribution Service}) ausgewählt. Die Hauptaufgabe der Kommunikationsschnittstelle ist die bidirektionale Konvertierung zwischen \gls{DDS}- und \gls{JSON}-Nachrichten. Sowohl für \gls{JSON} als auch für \gls{DDS} werden spezialisierte Softwarebibliotheken verwendet. Das Modul implementiert die Nachrichtenstrukturen und die nötigen Parsing-Funktionen, um die Daten zwischen den Formaten zu übersetzen.

In der prototypischen Umsetzung wird die \gls{DDS}-Bibliothek \textit{Fast DDS} der Firma eProsima verwendet. C++ kann als eine Erweiterung von C betrachtet werden, und C-Code ist in der Regel auch in einer C++-Umgebung lauffähig. \textit{eProsima Fast DDS} ist eine weit verbreitete Implementierung, die auch im \gls{ROS} 2 Ökosystem verwendet wird. Das Kommunikationsmodul selbst wurde ebenfalls hauptsächlich in C++ implementiert, um eine einfachere Integration mit der C++-basierten \gls{DDS}-Bibliothek zu ermöglichen.

Die Erstellung und das Auslesen von \gls{JSON}-Daten wurde hingegen mit Hilfe der Softwarebibliothek \texttt{cJSON} implementiert. Da \texttt{cJSON} in C geschrieben ist, lässt es sich problemlos auch in C++-Projekte integrieren.

Beim Start verbindet sich die Kommunikationsschnittstelle mit dem Kommunikationssockel von Runtime Node oder Runtime Master und startet die konfigurierten DDS Publisher und Subscriber. Wird eine Nachricht über einen DDS Subscriber empfangen, werden die Daten in eine interne Datenstruktur kopiert. Aus dieser Struktur wird mithilfe von \texttt{cJSON} die entsprechende \gls{JSON}-Nachricht erstellt und über den lokalen Socket versendet. Umgekehrt werden aus empfangenen \gls{JSON}-Nachrichten die Daten in die interne Datenstruktur kopiert und anschließend als \gls{DDS}-Nachricht versendet. Das Modul ist so generisch implementiert, dass es identisch sowohl für den Runtime Node als auch für den Runtime Master einsetzbar ist. Dadurch müssen nicht mehrere Varianten gepflegt werden.

\section{Implementierung Runtime Master}
\label{sec:ImplementierungRuntimeMaster}

Die Komponente Runtime Master ist für die Verwaltung der Runtime Nodes zuständig. Sie wird nicht auf Fahrzeugsteuergeräten, sondern einmalig pro Netzwerk auf einem zentralen Server ausgeführt. Da in der Informationstechnik hauptsächlich die x86-Architektur verwendet wird, ist die Portierbarkeit auf verschiedene Hardwarearchitekturen bei dieser Komponente weniger kritisch als beim Node. Bei der Auswahl der Programmiersprache bestanden daher weniger Einschränkungen. 

Für diese Komponente wurde eine Programmiersprache ausgewählt, die eine möglichst einfache und effiziente Implementierung von Netzwerkanwendungen ermöglicht. Die Programmiersprache Go (auch Golang genannt) wurde von Google entwickelt, um die Produktivität bei der Softwareentwicklung für Maschinen mit mehreren CPU-Kernen sowie für vernetzte Systeme zu steigern. Die Syntax von Go ähnelt der von C, bietet jedoch erweiterte Funktionalitäten wie \textit{Goroutines}, die die Erzeugung und das Scheduling von Threads vereinfachen, sowie mächtige Standardbibliotheken für Netzwerkprotokolle. Aus diesen Gründen wurde Go für die Implementierung des Runtime Master verwendet.

\subsection{Implementierung Node-Datenbank}
Die Node-Datenbank speichert die Informationen über alle Runtime Nodes, die sich aktuell im selben Netzwerk befinden. Diese Informationen werden über die in \autoref{sec:ImplementierungBefehlsverarbeitung} vorgestellten \texttt{Node Info} Nachrichten übertragen. Die Datenbank beinhaltet alle Informationen aus den Nachrichten; zusätzlich wird festgehalten, wann die letzte Nachricht empfangen wurde, um Timeouts zu erkennen. 

In der prototypischen Implementierung ist die Datenbank als interne In-Memory-Datenstruktur umgesetzt. Diese Methode speichert alle Einträge im Arbeitsspeicher des Systems. Je nach Objektgröße können so problemlos 100.000 Einträge verwaltet werden. Diese sind jedoch nicht persistent, da die Datenstruktur nach Beenden der Applikation gelöscht wird. Für größere Netzwerke mit vielen Teilnehmern und der Anforderung an Persistenz ist es sinnvoll, auf eine externe Datenbanklösung zurückzugreifen. Datenbanken sind eigenständige Softwarekomponenten, die Daten persistent auf die Festplatte schreiben und eine standardisierte API bieten. Für diese Anwendung können relationale Datenbanken (z.\,B. SQL) sinnvoll verwendet werden. In einer solchen Struktur werden die Daten in tabellarischer Form gespeichert. Jede Runtime Node erhielte einen eigenen Tabelleneintrag. Die Container der Nodes würden ebenfalls in einer eigenen Tabelle gespeichert, die relational mit der Node-Tabelle verknüpft ist. Dies erlaubt eine effiziente Speicherausnutzung.

\subsection{Implementierung Benutzeroberfläche}
Die Benutzeroberfläche wurde als grafische 2D-Bedienoberfläche implementiert. Sie ermöglicht es Nutzern, die Runtime Nodes manuell zu kontrollieren und deren Statusmeldungen zu visualisieren sowie die enthaltene Applikationen. \autoref{fig:gui_screenshot} Diese Visualisierung dient im Prototyp zur Validierung der Discovery-Funktionalität und ermöglicht dem Operator eine schnelle Übersicht über die Cluster-Topologie. Für die Implementierung wurde die Softwarebibliothek \textit{Dear ImGui} verwendet. ImGui ist eine C++-Bibliothek, für die jedoch Wrapper für andere Programmiersprachen existieren. Go kann mithilfe der \texttt{cgo}-Mechanik C-Funktionen aufrufen. Der verwendete Wrapper implementiert ein Interface für ImGui sowie Go-Bindings, die diese Funktionen aufrufen. 

Es wurden vier Hauptfenster implementiert:
\begin{itemize}
    \item \textbf{Befehlsfenster:} Erlaubt das manuelle Senden von Befehlen an die Runtime Nodes. Container können hier durch den Benutzer manuell verwaltet werden.
    \item \textbf{Statusfenster:} Zeigt die verfügbaren Runtime Nodes im Netzwerk an, deren Verfügbarkeitsstatus, Ressourcen sowie enthaltene Applikationen.
    \item \textbf{Log-Fenster:} Zeigt die letzte Statusrückmeldung des Runtime Nodes an, welcher den letzten Befehl erhalten hat.
    \item \textbf{Transfer-Fenster:} Ermöglicht das Übertragen von Daten in ausgewählte Container.
\end{itemize}

In der prototypischen Implementierung sind die einzelnen Softwarekomponenten nicht als eigenständige Prozesse, sondern als \textit{Goroutines} (Threads) realisiert. Durch diese Architektur kann die Benutzeroberfläche direkt auf die Funktionen und Datenstrukturen der anderen Komponenten zugreifen.

\subsection{Implementierung Nachrichtenverwaltung}
Die Runtime Master-Komponente empfängt diverse Nachrichten von den Runtime Node-Komponenten. In diesem Modul werden diese Nachrichten ausgewertet und an die passenden Subkomponenten weitergeleitet. Grundsätzlich werden drei verschiedene Nachrichtenkategorien unterschieden:

\begin{itemize}
    \item \textbf{Info-Nachrichten:} Diese beinhalten entweder eine \texttt{Node Info} oder \texttt{Interface Info} Nachricht.
    \item \textbf{Befehls-Rückmeldungen:} Diese enthalten die Statusrückmeldungen der Runtime Nodes auf empfangene Befehle.
    \item \textbf{Datentransfer-Nachrichten:} Diese sind Statusrückmeldungen während einer Dateiübertragung.
\end{itemize}

Kann eine empfangene Nachricht keiner der Kategorien zugeordnet werden, wird diese ignoriert. Wird eine Nachricht erfolgreich zugeordnet, so werden die empfangenen Daten aus dem \gls{JSON}-Format in eine interne Go-Datenstruktur konvertiert. Die Nachrichtenverwaltung ruft im Anschluss die passenden Funktionen der anderen Softwarekomponenten auf. Im Runtime Master wird anstelle von \texttt{cJSON} die in der Go-Standardbibliothek enthaltene \texttt{encoding/json} Bibliothek verwendet, da diese eine nahtlose Integration in die Sprache bietet.

\subsection{Implementierung des Ladens externer Applikationen}
Das Gegenstück zum Dateiempfang im Runtime Node (\autoref{sec:LadenExterneApplikationenNode}) ist die Sende-Implementierung im Master. Diese ist ebenfalls als State Machine mit den Zuständen \texttt{Idle}, \texttt{Running} und \texttt{Done} realisiert. 

Um die Datenübertragung zu starten, muss zunächst ein Ziel-Node und ein Container ausgewählt werden. Anschließend werden der lokale Dateipfad sowie der Zielname im Container spezifiziert. Der Datentransfer wird durch eine Startnachricht ausgelöst, die beim Runtime Node anfragt, ob dieser empfangsbereit ist. Nach positiver Rückmeldung wechselt die State Machine in den \texttt{Running}-Zustand. Die Datei wird blockweise binär ausgelesen, mittels Base64 kodiert und in \gls{JSON}-Nachrichten verpackt. Die Struktur ist identisch zur Darstellung in \autoref{fig:JSON_binary}. 

Da die \gls{JSON}-Nachricht maximal 3.072 Bytes groß ist (davon ca. 2.307 Bytes Nutzdaten), wird die Datei in Pakete aufgeteilt. Der Prozess erfolgt synchron: Das nächste Paket wird erst gesendet, wenn der Runtime Node den Empfang des vorherigen bestätigt hat. Sobald alle Teilstücke übertragen wurden, sendet der Master den Befehl \texttt{end\_exchange} und wechselt in den \texttt{Done}-Zustand. Interne Variablen werden zurückgesetzt, und das System ist bereit für den nächsten Transfer.

\section{Implementierung und Evaluation des Schedulers}
\label{sec:ImplementierungScheduler}

Der Scheduler hat die Aufgabe, externe Applikationen automatisch nach bestimmten Optimierungskriterien auf die verfügbaren Runtime Nodes zu verteilen. Eine Auswahl theoretischer Methoden wurde in \autoref{ch:MethodeSoftwareplattform} vorgestellt. Da die Softwareplattform aktuell prototypisch vorliegt und keine physische Flotte von Hunderten Fahrzeugen zur Verfügung steht, wurden die Scheduling-Methoden simulativ implementiert und ausgewertet.

Das Problem wurde als multiobjektives Multi-Knapsack-Problem modelliert. Für die Simulation werden Methoden untersucht, die auf dieses Problem anwendbar sind.

\subsection{Gewichtung von Optimierungskriterien}
Die \texttt{Node Info} Nachricht liefert mehrere Metriken, die für die Optimierung herangezogen werden können. Um die verfügbare Rechenleistung der Flotte möglichst effizient zu nutzen, muss primär eine Optimierung der Ressourcenauslastung erfolgen. Hierzu werden die drei Hauptressourcen verwendet:
\begin{itemize}
    \item CPU-Leistung (TOPS)
    \item Arbeitsspeicher (RAM)
    \item Massenspeicher (Storage)
\end{itemize}

Für den Anwendungsfall \enquote{Verteiltes Rechnen im Fahrzeug} ist das Finden der exakten mathematischen Optimallösung weniger wichtig als eine schnelle Entscheidungsfindung für eine große Menge an Nodes. Das Hauptoptimierungskriterium ist die CPU-Auslastung. RAM und Speicher werden als harte Grenzwerte (\textit{Constraints}) betrachtet, die nicht überschritten werden dürfen, aber nicht zwingend maximiert werden müssen. Die Optimierung erfolgt daher primär nach CPU-Auslastung unter Einhaltung der Speicherlimits.

\subsection{Implementierung der Scheduling-Algorithmen}
\label{sec:ImplementierungAlgorithmen}

In \autoref{ch:MethodeSoftwareplattform} wurde eine Auswahl gängiger Algorithmen vorgestellt. Um die Qualität des zu wählenden Algorithmus bewerten zu können, wurde eine Vergleichssimulation durchgeführt. Das Ziel ist es, die CPU-Auslastung auf allen Runtime Nodes möglichst hoch zu halten.

Es wurden drei fundamentale Algorithmen verglichen, wobei sowohl die Lösungsgüte als auch die benötigte Rechenzeit ausgewertet wurden:
\begin{itemize}
    \item \textbf{Brute Force:} Berechnet alle möglichen Permutationen und wählt die beste Lösung. Garantiert das globale Optimum, ist aber extrem rechenintensiv.
    \item \textbf{First-Come-First-Serve (FCFS):} Eine simple Methode ohne Optimierung. Aufgaben werden in der Reihenfolge ihres Eintreffens dem erstbesten passenden Node zugewiesen.
    \item \textbf{Greedy:} Sortiert Aufgaben nach ihrer Größe (Auslastung) und weist die größte Aufgabe dem bestmöglichen Node zu.
\end{itemize}

Für die Simulation wurden Nodes mit Eigenschaften angenommen, die aktuellen Level-4-Steuergeräten entsprechen (siehe \autoref{ch:StandDerTechnik}):
\begin{itemize}
    \item Rechenleistung: $1000 - 2000$ TOPS
    \item RAM: $64$ GB
    \item Speicher: $500$ GB
\end{itemize}

Die zu verteilenden Aufgaben wurden mit folgenden Anforderungen modelliert:
\begin{itemize}
    \item Benötigte Rechenleistung: $500 - 1000$ TOPS
    \item RAM: $20 - 50$ GB
    \item Speicher: $100 - 300$ GB
\end{itemize}

In einer ersten, kleinen Simulation wurden 11 Aufgaben auf 3 Nodes verteilt. Die Problemgröße wurde bewusst klein gehalten, da die Berechnungszeit für \enquote{Brute Force} exponentiell ansteigt.

\begin{itemize}

\end{itemize}

Es entstehen keine signifikanten Leerlaufzeiten durch den Scheduling-Prozess selbst.

Die Simulation bestätigt die Eignung der Architektur für den Einsatz in Fahrzeugnetzwerken. Durch die \enquote{Retry} Logik wird eine Zuverlässigkeit von 100\% (kein Aufgabenverlust) erreicht. Allerdings ist dies mit erhöhtem Latenz verbunden: Aufgaben, die auf einem Knoten unterbrochen werden, müssen neu gestartet werden. Die hohe Systemauslastung beweist jedoch, dass die gewählte Strategie (Greedy TOPS Prio) die teure Hardware Ressource auch unter dynamischen Bedingungen effizient nutzt.

\section{Zusammenfassung}

In diesem Kapitel wurde die erfolgreiche Implementierung der Softwareplattform detailliert beschrieben. Der Runtime Node wurde in C realisiert, um eine hohe Hardwarenähe und direkten Zugriff auf Linux-Kernel-Features zu gewährleisten. Der Runtime Master wurde in Go implementiert, um von dessen Nebenläufigkeitsmodell bei der Verwaltung vieler Knoten zu profitieren. Die Kommunikation erfolgt über eine modulare \gls{DDS}-Schnittstelle. Die abschließenden Simulationen verifizierten, dass der gewählte \enquote{Greedy (TOPS Prio)}-Algorithmus auch unter dynamischen Bedingungen eine hohe Ressourceneffizienz und Systemstabilität sicherstellt.
